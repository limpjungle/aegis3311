# Деградационный режим

> Выдержка из [architecture.md](../00-overview/architecture.md) §5, шаг 6. Источник истины — исходный документ: правки вносить туда, затем синхронизировать этот файл.

## Шаг 6. Деградационный режим

Принцип: потеря связи сужает полномочия, а не продолжает работу «как обычно».

1. **Вход по lease.** Агент переходит в режим по истечении lease, а не по таймауту пинга: это исключает split-brain при частичной потере связи. Control Plane не выдаёт изменяющих команд кластеру без действующего lease.
2. **Разрешённый набор.** Только предодобренные детерминированные действия класса R1 (R2 — если разрешает политика) по кэшированным политикам. По истечении TTL кэша — read-only.
3. **Без свободного reasoning.** Выбор действий силами LLM отключён. Малая локальная модель опциональна и допускается только для суммаризации и классификации (открытый вопрос в §11).
4. **Локальный аудит.** Действия пишутся в собственную подписанную цепочку агента.
5. **Восстановление.** Цепочки сливаются и сверяются с audit Control Plane, локальные действия проверяются на конфликт с текущим состоянием. Прежние уровни возвращаются после реконсиляции.

### Хранилище состояния LLM-роутера (Этап 0a)

- `ErrCorrupt`, `ErrVersion` или `ErrIdentity` при старте (`internal/routerstate`) — роутер не создаётся, LLM недоступен, цели не выше L1. Файл хранилища переносится в сторону для разбора; при старте с пустым хранилищем роутер встанет в `state_lost`. SRE сверяет расход токенов по decision record'ам и делает `Resume`.
- Halt `state_store` (сбой записи во время работы; запросы `not_sent`/`halted`, L1) — проверить диск, перезапустить процесс; если после рестарта halt восстановился по цепочке аудита, снять его через `Resume`.
- Halt `chain_lost` (цепочка аудита пуста, а хранилище состояния содержит учёт: удалена или подменена цепочка; **при настроенном `audit.anchor` и существующих checkpoint'ах пустая цепочка не откроется вовсе** — отказ старта `anchor_mismatch`, см. ниже; `chain_lost` остаётся для развёртываний без anchor) — роутер при старте пишет новый якорь `state_created` и `router_halted(chain_lost)` в новую цепочку и стоит до `Resume`. Бюджеты сохранены (они берутся из store), но предыдущая история аудита потеряна: оператор восстанавливает цепочку из WORM-копии/бэкапа (перед `Resume` проверить `aegis-audit verify`), фиксирует инцидент безопасности и только затем делает `Resume`. Одновременное удаление store и цепочки неотличимо от первого запуска (остаточный риск). Если запись `router_halted(chain_lost)` не удалась, остановка всё равно сохраняется в store, и событие дописывается в цепочку при следующем старте.
- Halt `state_lost` (пустое хранилище при непустой цепочке: в цепочке есть любая запись; при старте с пустой цепочкой роутер пишет якорь `state_created`, поэтому удаление store после первого старта всегда даёт `state_lost`) — расход за сутки и по инцидентам обнулён (бюджеты из цепочки не восстанавливаются), а состояние failover (down/quarantine, активный endpoint) восстановлено из событий цепочки; закрепления инцидентов не восстанавливаются (после `Resume` закреплённый за fallback инцидент может уйти на primary — приемлемо); снимает только человек через `Resume`, решение попадает в аудит. Если не удалась запись якоря `state_created` (или события `router_halted` оборванного перехода) в аудит, роутер не создаётся (`ErrAuditFailed`): починить аудит и перезапустить процесс; при отказе записи intent в store `New` возвращает `ErrStateStore`. `state_lost` затирает прежнюю причину halt (например `auth`): после `Resume` следующий запрос может снова дать `auth`, поэтому перед `Resume` оператор проверяет последние `router_halted` в цепочке. При одновременном отказе store и auth/estimator halt пишется как `state_store`, сигнал 401 (или превышения контекста) в аудит не попадает.
- Halt `egress_canary` (в теле запроса к LLM найден canary-маркер из `canary.markers_file`; как и `auth`/`estimator`, это остановка роутера до `Resume`) — запрос не отправлен (`not_sent/egress_canary`, L1), роутер остановлен, в цепочке `router_halted(egress_canary)`, горит `IntakeEgressCanaryDetected`. Это инцидент безопасности: маскировщик пропустил данные, которые не должны уходить наружу. Security разбирает (decision record, `llm.sources`), правит маскировщик и/или переводит источник в restricted PR'ом в `internal/dataclass` (`require: security`); только после этого `Resume` (процедура ниже). Маркеры из файла в журнал не пишутся. Если задан `snapshot_dir`, снимок входа заблокированного запроса (`<input_sha256>.json`, 0600) сохраняется и содержит непойманный маркер вместе с окружающими данными — это улика для разбора, но и копия утёкших данных на диске пода: после разбора Security удаляет снимок, не дожидаясь 90 суток. Откат бинаря ниже rollback floor после этой записи невозможен, см. [migrations.md](migrations.md) «Откат»; снимать canary — удалением блока `canary`, не откатом образа.

#### Сверка с WORM на старте (`audit.anchor`, 09.11.2026)

- `anchor_unavailable` — хранилище checkpoint'ов недоступно при старте (сеть, bucket, ключи, сертификат, таймаут): сервис не стартует, код выхода 1 (`ErrAnchorUnavailable`), файлы не создаются. Восстановить доступ и перезапустить; обходить сверку, убирая `audit.anchor`, можно только решением Security с записью в журнал инцидентов.
- `anchor_mismatch` — цепочка не совпала с checkpoint'ом (усечена, откатена к старой копии, переписана, пуста при существующих checkpoint'ах; либо delete marker или чужой ключ в префиксе checkpoint'ов): `ChainError`, код 1. Это инцидент безопасности: цепочку не править; восстановить файл из бэкапа, самое свежее состояние которого не короче последнего checkpoint'а, проверить `aegis-audit verify -anchor-config FILE` и только затем стартовать. Файл цепочки удалён или пуст при существующих checkpoint'ах: то же — восстановить файл из бэкапа (не короче последнего checkpoint'а); если бэкапа нет, потерянную историю не воссоздать — Security решает завести новый `chain_id` (checkpoint'ы старой цепочки остаются в WORM как свидетельство, новая цепочка сверяется со своим префиксом), с записью в журнал инцидентов.
- Отставание фиксации (`aegis_intake_audit_anchor_lag_seconds` > `max_lag`, лог `audit_anchor_lagging`) запись не останавливает: проверить bucket, ключи, срок действия сертификата. Остановка изменяющих действий по переполнению — G1 (CH-A14).

#### Процедура оператора: `aegis-llmrouter` (07.11.2026)

Операторские команды выполняются офлайн: писатель цепочки и store единственный, при работающем `serve` команды получают код 3.

1. `systemctl stop aegis-llmrouter`.
2. `aegis-llmrouter status -config FILE` — проверить `halted`, `halt_reason` и `last_router_halted` (причину, записанную в цепочку). `status` проходит полную сверку старта, как рестарт: может дописать событие и списать незакрытые резервы.
3. Для `chain_lost` — восстановить цепочку из WORM-копии и проверить `aegis-audit verify`. Для `state_lost` — сверить расход по decision record'ам. Для `state_store` и `audit_failed` — проверить диск и ключ подписи.
4. `aegis-llmrouter resume -config FILE -operator ID` — снимает остановку и карантин, пишет `router_resumed`. Если роутер не остановлен и карантина нет, команда завершается с кодом 1 и ничего не пишет.
5. `systemctl start aegis-llmrouter`.

Коды выхода: 0 — успех; 1 — fail-closed (store, цепочка или аудит повреждены или отказали; для `ErrCorrupt`, `ErrVersion`, `ErrIdentity` и `ChainError` см. пункты выше); 2 — аргументы, конфигурация, окружение (в том числе сервис ещё не запускался); 3 — файлы заняты работающим процессом (запущен `serve`: остановите сервис). Ошибка health-loop завершает `serve` с кодом 1, перезапуск — за супервизором; остановку, восстановленную при старте, снимает `resume`.

Конфигурация (JSON, без секретов; секреты — в `OPENROUTER_API_KEY_FILE`, `AEGIS_MASKER_KEY_FILE`, `AEGIS_AUDIT_KEY_FILE`):

```json
{"router_id": "llmrouter-1", "state_path": "/var/lib/aegis/llmrouter.state",
 "audit": {"chain": "/var/lib/aegis/audit.jsonl", "chain_id": "aegis-prod", "public_keys": []},
 "failover": {"fail_threshold": 3, "hysteresis": "10m", "health_interval": "30s"}}
```

### Kill switch (Этап 0a)

Устройство — [architecture.md](../00-overview/architecture.md) §2.2, учение — [kill-switch-drill.md](kill-switch-drill.md).

- **Каналы недоступны или нет свежего подтверждения → остановка.** Транспортный сбой одного канала допустим до TTL подтверждения (кэш), затем intake переходит в `no_confirmation`: сбор идёт, роутер в режиме `off`, `llm.mode=off` в записях, PEP получает `liveness_confirmed=false`. Это штатное безопасное направление; проверьте `aegis-killswitch status` и журнал (`kill_switch_channel` с классом ошибки).
- **Продление встало** (renewer не работает, один из двух не отвечает, `waiting_peer` в выводе): в журнале intake предупреждение `kill_switch_confirmation_expiring` (до конца подтверждения меньше трети TTL). Починить renewer либо вручную опубликовать подтверждение двумя дежурными: `aegis-killswitch release -out` → второй дежурный `cosign -publish`.
- **Действующий stop блокирует продление** (renewer отказывает): снять остановку может только `release` двух дежурных, документ должен быть новее stop.
- **Сбой записи события в цепочку** при снятии — intake остаётся остановленным и завершается с кодом 1 (fail-closed): починить диск и перезапустить.
- **Bootstrap после потери цепочки.** Новая цепочка (или цепочка без события с `stop_watermark`) = история kill switch потеряна: первая оценка выставит `W` по часам intake, intake будет в `no_confirmation` (`bootstrap_awaiting_release=1`), пока двое дежурных не опубликуют release с `issued_at` позже `stop_watermark`; старый свежий run не поможет. Перед этим обязательно `aegis-audit verify` старой цепочки и checkpoint'ов: если потеря неожиданная (файл пропал или откатился к старой копии, а не штатная замена) — разбор как инцидента безопасности (T-23), а не повод просто опубликовать release.
- **Реакция на алерты kill switch** (правила — [intake-deploy.md](intake-deploy.md), шаг 7). `KillSwitchRenewalMissed` / `KillSwitchConfirmationExpiring`: проверить оба renewer (`aegis-killswitch renew`, вывод `peers`: `http_403` — права/ListBucket, `missing` — коллега не подписал), при необходимости опубликовать подтверждение вручную (release двумя дежурными). `KillSwitchCheckStale`: сломан сам check (хост, cron, права) — до починки наблюдения нет, проверять `aegis-killswitch status` вручную. `KillSwitchChannelDown`: канал не читается (RBAC, egress, bucket); один канал — деградация, оба — `no_confirmation` через TTL. `IntakeKillSwitchNoConfirmation`: intake остановлен без подтверждения — как «продление встало»; не бывает при `bootstrap_awaiting_release=1`. `IntakeKillSwitchBootstrapAwaitingRelease`: после старта не опубликован release. После рестарта признак известен, только если последнее событие цепочки — bootstrap; иначе (или на цепочке старой сборки) вместо него сработает `IntakeKillSwitchNoConfirmation` — действие то же: release двумя дежурными позже `stop_watermark`. `IntakeKillSwitchPollStale`: монитор не опрашивает каналы — смотреть журнал и процесс. `IntakeKillSwitchDisagree`: check видит работу, intake стоит — `W` новее подтверждения (bootstrap, стёртый stop), `aegis_intake_killswitch_channel_ok == 0` (RBAC/egress intake) или часы intake; сверить `stop_watermark` в `/metrics` и `release_watermark`. `IntakeMetricsDown`: нет скрейпа (listener, NetworkPolicy), сам intake может работать. `IntakeRouterHalted`: причина в `aegis_intake_router_halt_reason`, `aegis-llmrouter status`/`resume`.
- **`kill_switch_channel_regressed`** в журнале intake (`older_document` — в канале документ старше виденного; `stop_removed` — stop исчез): кто-то записал канал не процессом публикации (ConfigMap без ключей подписи, подмена объекта). Возможная компрометация пишущего: инцидент безопасности. Сразу проверить аудит Kubernetes на запись ConfigMap, сверить версии объекта в S3, опубликовать stop заново (оба канала). После каждого stop — проверить событие, `check` и `aegis_intake_killswitch_stopped`.

### Intake (`aegis-intake`, Этап 0a)

`aegis-intake serve` сам держит роутер (цепочку и store), поэтому процедура оператора `aegis-llmrouter` выполняется при остановленном intake: `systemctl stop aegis-intake` → `aegis-llmrouter status/resume` (см. выше) → `systemctl start aegis-intake`. Одновременный запуск `aegis-llmrouter serve` и `aegis-intake serve` даёт код 3.

- **Источник недоступен** (Kubernetes, Prometheus; критичные: топология, метрики целиком, rollout, db). Сбор повторяется до 2 раз с паузой 30 с внутри `settle + 5 мин`, затем в цепочку пишется запись `intake.outcome=not_routed`, `reason=source_unavailable`, модель не вызывается (уровень не выше L1 для этого инцидента — предложения нет). Статусы и класс ошибки каждого источника — в `intake.sources`. Некритичные источники (`events`, `deploys`, `pdb`, отдельные метрики) дают статус `unavailable` и пустую секцию; запрос уходит.
- **Alertmanager недоступен.** Опрос завершается ошибкой (предупреждение `intake_poll_failed` в журнале), открытые инциденты не трогаются и не закрываются: недоступность разрешением не считается. Новые инциденты не открываются до восстановления.
- **Повреждённое состояние intake** (`ErrStateCorrupt`, код 1). Перенесите файл `state_path` в сторону и запустите снова: пустое состояние безопасно, дубли записей отсекает цепочка аудита по детерминированному ID инцидента (`HasIncidentRecord`); последствия — открытые инциденты начнутся заново с `startsAt` первого текущего алерта, закрытие в роутере произойдёт по обычному правилу. Занятый файл (`ErrStateLocked`, код 3) — запущен другой `aegis-intake`.
- **Роутер остановлен** (halt): `Route` возвращает `not_sent` (`halted`, `unavailable`, `budget_*`) — запись пишется с блоком `llm`, `outcome=routed`; закрытие инцидентов повторяется на каждом опросе, пока `CloseIncident` не пройдёт. Снятие остановки — по процедуре выше.
- **Сбой аудита или store** — `aegis-intake` завершается с кодом 1 (fail-closed), перезапуск — за супервизором; после рестарта необработанные инциденты обрабатываются заново (не более 3 попыток на инцидент, затем `not_routed/attempts_exhausted`).
- **Остановка во время обработки.** Если `aegis-intake` останавливают во время сбора или вызова модели, запись не пишется: инцидент остаётся `open` и после рестарта обрабатывается заново (повторный расход ограничен 3 попытками и бюджетом инцидента).
- **Снимки входа** лежат в `snapshot_dir` (`<input_sha256>.json`, 0600), хранятся 90 суток; сбой записи снимка не мешает записи решения (предупреждение в журнале).
