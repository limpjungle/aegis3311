# Жизненный цикл инцидента

> Выдержка из [architecture.md](../00-overview/architecture.md) §5, шаг 5. Источник истины — исходный документ: правки вносить туда, затем синхронизировать этот файл.

## Шаг 5. Эксплуатация и самовосстановление (Day-2)

1. **Приём инцидентов.** Алерты из Alertmanager, PagerDuty или Opsgenie, дедупликация и корреляция, создание инцидента, назначение владельца (человек или агент), ChatOps.
2. **Масштабирование** — три контура из §2.4.
3. **Self-healing.** Цепочка: детекция → классификация → выбор действия каталога → PEP (политика, уровень, лимиты, lease) → песочница для нетиповых действий → исполнение по уровню → пост-проверка → откат при провале.
   - **Предодобренные runbook'и** с историей успехов идут без песочницы: в инциденте у неё ограниченный бюджет времени.
   - **Песочница** (staging-реплика и shadow-трафик) — для нетиповых действий. Реплей запросов на запись только со стабами внешних зависимостей (платежи, почта) и маскированием PII; по умолчанию read-only.
   - **Пример: забитый пул PostgreSQL.** Диагностика (сессии idle in transaction, утечка в клиенте) → изменение размера пула PgBouncer через reload в границах (L2, при накопленной статистике L3) + PR с исправлением утечки. `max_connections` и `shared_buffers` требуют рестарта СУБД — это L1: карточка в Slack с кнопкой «Применить».
4. **Bare Metal.** Штатные операции Ceph/IPMI/сети — L2 с окном отмены, необратимые — L1.
5. **Закрытие цикла.**
   - ИИ готовит отчёт (логи, хронология, timeline событий); SRE утверждает его до попадания в базу знаний.
   - Записи runbook'ов получают версию, окружение и срок годности (TTL); устаревшие требуют ревалидации.
   - Инженер оценивает каждое действие ИИ (+/- и комментарий). Не сработавшие runbook'и понижаются в приоритете.
