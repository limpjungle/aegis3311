# Матрица ответственности (RACI)

> Основа — [architecture.md](../00-overview/architecture.md) §9 (роли, ответственность); [plan.md](../01-planning/plan.md) §2 (кто решает по gates). Распределение ответственности ведётся в этом файле.
>
> Статус: **проект на утверждение**. Исходная предпосылка — пять ролей заняты разными людьми.

## 1. Роли

| Роль | Зона |
|---|---|
| **Оператор платформы** | Эксплуатация AegisOps: Control Plane, агенты, роутер, политики как код, каталог действий. Автор изменений политик и каталога |
| **SRE-лид** | Качество и безопасность автономных действий: уровни автономности, runbook'и, решения по gates G0–G2 |
| **Владелец сервиса** | Сервис, над которым действует агент: допуск сервиса к пилоту, последствия действий для сервиса, SLO |
| **Security** | Модель угроз, классы данных, red-team, identity и секреты, согласования Этапа −1 |
| **Аудитор** | Независимая проверка: аудит действий, соответствие процессам. Только чтение |

Дополнительные участники из [plan.md](../01-planning/plan.md) §2: **спонсор** (G(−1)), **владелец инфраструктуры** (G3c), **владелец ML** (G4), **DPO / юристы** (152-ФЗ, GDPR). On-call инженер исполняет оперативные шаги от имени владельца сервиса.

**Агент** — не роль RACI. Он не бывает ни A, ни согласующим и не может стать вторым подтверждающим в принципе четырёх глаз.

### 1.1 Как разделена ответственность за действия агента

Архитектура называет ответственными за действия агента владельца сервиса и оператора платформы. В RACI у каждой строки ровно один A, поэтому зоны разделены:

- **Последствия действия для сервиса** (допустимо ли действие для этого сервиса и его SLO) — A у владельца сервиса.
- **Корректность платформы** (политика проверена, lease действовал, аудит записан, откат сработал) — A у оператора платформы.

## 2. Обозначения

**R** — выполняет; **A** — отвечает и принимает решение (ровно один на строку); **C** — консультирует до решения; **I** — информируется после.

## 4. Правила

1. **Четыре глаза — это два разных человека с разными ролями.** Автор изменения — оператор платформы, подтверждающий — SRE-лид, по политикам безопасности — ещё и security. Один человек не может быть и автором, и подтверждающим, даже если он временно совмещает роли.
2. **Агент не может подтверждать.** Его identity технически исключена из групп подтверждающих (CODEOWNERS, branch protection, RBAC).
3. **Аудитор не меняет ничего.** У роли только чтение аудита и конфигурации; записи в audit log не может изменить никто.
4. **Замещение.** Для каждой роли назначен заместитель. Отпуск или болезнь не должны вынуждать совмещать автора и подтверждающего.
5. **Kill switch может нажать любой on-call** (R), но снять — только по принципу четырёх глаз.

## 5. Открытые вопросы

1. Кто конкретно назначен в каждую роль и кто заместители.
2. Нужен ли отдельный A для решений по стоимости: бюджеты LLM и инфраструктуры.
3. Кто представляет DBA при изменениях `postgres.*` и `pgbouncer.*`: отдельная роль или владелец сервиса.
