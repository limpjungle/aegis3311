# Классы данных и политика LLM

> Основа — [architecture.md](../00-overview/architecture.md) §3 (строка «Утечка данных во внешний LLM»), §6.2, §9. Принципы правятся там. Детализация в этом файле ведётся здесь.
>
> Статус: **проект на утверждение** (Этап −1, gate G(−1)). Значения, помеченные *(предложение)*, нужно утвердить с security и юристами. Правовые утверждения — ориентир для юристов, а не юридическое заключение.

## 1. Решение по LLM

Пользователи выбирают **LLM-профиль** (§1.2). Профиль по умолчанию — **hybrid** (комбинированная схема):

| Роль модели (§6.2) | Где работает | Какие классы данных получает |
|---|---|---|
| `local-small` | Локально, в юрисдикции данных | Все, кроме секретов: классификация, суммаризация, маскирование |
| `local-large` | Локально, в юрисдикции данных | Все, кроме секретов, включая restricted: reasoning по немаскированному контексту |
| `external-reasoning` | **OpenRouter** с принудительным ZDR (§1.1) | public, internal; confidential — только после маскирования и только при выполнении условий §4 |

Секреты (ключи, токены, пароли, строки подключения) не передаются **ни в одну** модель, включая локальные: их вырезают до роутера.

При недоступности OpenRouter запрос уходит в `local-large`. Если не справляется и она, затрагиваемые цели понижаются до L1 (§6.2).

### 1.1 OpenRouter: что учитывать

OpenRouter — агрегатор: запрос проходит через OpenRouter и уходит к одному из upstream-провайдеров модели. Поэтому условия хранения данных действуют на двух уровнях, и оба нужно контролировать.

**Обязательные настройки:**

| Настройка | Значение | Зачем |
|---|---|---|
| ZDR на уровне аккаунта | Включено | Маршрутизация только на endpoint'ы с zero data retention. Действует, даже если запрос забыл указать флаг |
| `provider.zdr` в каждом запросе | `true` | Дублирует аккаунтную настройку; роутер Aegis отклоняет запрос без этого поля |
| `provider.data_collection` | `"deny"` | Исключает endpoint'ы, которые хранят данные или обучаются на них |
| Логирование промптов в OpenRouter | Выключено (opt-in не делать) | По умолчанию OpenRouter промпты не хранит; включение логирования отменяет это |
| Явный список upstream-провайдеров и запрет fallback'а на остальных | Закреплён для каждой модели (`provider.order` / `only`, `allow_fallbacks: false`) | Модель у разных провайдеров отличается: квантование, лимиты контекста, поведение. Без закрепления eval-результаты не воспроизводятся (§6.3) |
| Встроенные инструменты (web search и др.) | Выключены | ZDR распространяется только на инференс; инструменты обслуживают третьи стороны со своими условиями |
| BYOK (свои ключи upstream-провайдеров) | Не использовать без отдельного решения | OpenRouter не проверяет, соответствует ли заявленный ZDR по BYOK-ключу договору с провайдером |

**Что пишется в decision record:** slug модели, фактический upstream-провайдер из ответа, флаги `zdr` и `data_collection` запроса. Смена провайдера для закреплённой модели считается сменой модели и проходит через регрессионный eval.

**Ограничения, которые не снимаются настройками:**

- Список «no retention / no training» в OpenRouter отражает **опубликованные политики провайдеров**, а не гарантию их соблюдения. Поэтому правила классов (§2–4) остаются прежними: ZDR — дополнительная защита, а не основание отправлять больше данных.
- OpenRouter — американская компания, и подтверждённого региона обработки в ЕС или РФ я не нашёл. Любая отправка — трансграничная передача (§4).
- Доступность сервиса и оплата из РФ — отдельный операционный риск. Fallback на `local-large` обязателен и проверяется сценарием CH-A13 ([chaos.md](../05-testing/chaos.md)).

### 1.2 Выбор модели пользователем: LLM-профили

Команды и владельцы сервисов сами выбирают, работать только на локальных моделях или использовать внешнего провайдера, и какие именно модели. Выбор — это **предпочтение внутри политики**, а не способ её обойти.

**Режимы профиля:**

| Режим | Что происходит |
|---|---|
| `local-only` | Все роли (`local-small`, `local-large`, `external-reasoning`) обслуживают локальные модели. Во внешние сервисы не уходит ничего |
| `hybrid` | Роль `external-reasoning` обслуживает выбранный внешний провайдер, но только для классов, которые разрешают политика и допуски провайдера. Остальное — локально |
| `off` | LLM для сервиса не используется: ни внешний, ни локальный. Агент не формирует предложений; работают только детерминированные проверки и алерты. Аварийное сужение, доступно всегда, в том числе в MVP |

Режима «только внешний» нет: restricted-данные и данные с ПДн граждан РФ во внешний провайдер не уходят никогда (§2, §4). Если локальной модели в реестре нет (как в MVP, §1.3), такие данные просто не попадают в контекст LLM.

**Реестр моделей и провайдеров.** Пользователь выбирает только из утверждённого реестра. Для каждой записи указаны:

```yaml
# registry/llm-backends.yaml — меняется через PR, ревью security (четыре глаза)
backends:
  - id: openrouter
    kind: external
    jurisdiction: US
    max_class: confidential          # потолок допуска; ПДн граждан РФ запрещены (§4.2)
    pd_ru_allowed: false
    pd_eu_allowed: false             # true только после подписания DPA и DPIA
    required_request_flags: {zdr: true, data_collection: deny}
    models:                          # закреплённые модели и upstream-провайдеры (§1.1)
      - slug: z-ai/glm-5.3-flash-20260826   # датированный slug: алиас glm-5.3-flash может переехать на новую версию
        provider:
          only: [inceptron]              # endpoint inceptron/fp8, есть в списке ZDR OpenRouter (основной с 06.11.2026)
          quantizations: [fp8]
          allow_fallbacks: false
          zdr: true
          data_collection: deny
        eval_profile: ev-2026-11-or-01   # probe v1, промпт v2: допустимость 100%, вредные 0%
        fallback:                        # резервный endpoint; переключает роутер Aegis, а не OpenRouter (§1.4)
          provider:
            only: [wafer]                # endpoint wafer/us, есть в списке ZDR OpenRouter
            quantizations: [nvfp4]
            allow_fallbacks: false
            zdr: true
            data_collection: deny
          eval_profile: ev-2026-11-or-02   # probe v1, промпт v2: допустимость 98,8%, вредные 0%
  - id: local-ru
    kind: local
    jurisdiction: RU
    max_class: restricted
    models:
      - {name: <local-large-model>, role: local-large, eval_profile: ev-2026-11-lr-01}
      - {name: <local-small-model>, role: local-small, eval_profile: ev-2026-11-ls-01}
```

**Уровни выбора и наследование.** Профиль задаётся на уровне организации (по умолчанию), команды и сервиса. Нижний уровень может только **сужать** верхний: если организация выбрала `local-only`, сервис не может включить `hybrid`.

```yaml
# llm-profiles/team-payments.yaml
profile:
  scope: team/payments
  mode: hybrid
  external_backend: openrouter
  external_model: <vendor>/<model>@<version>
  local_backend: local-ru
  overrides:
    - scope: service/payments-ledger
      mode: local-only               # сужение для отдельного сервиса
```

**Итоговый маршрут** каждого запроса — пересечение ограничений, побеждает самое строгое:

1. класс данных запроса (§2–3);
2. юрисдикция данных и правила §4 (ПДн граждан РФ → только `local-ru`);
3. потолок допуска провайдера из реестра (`max_class`, `pd_*_allowed`);
4. LLM-профиль сервиса, унаследованный от команды и организации.

Если ни один разрешённый backend не может обслужить запрос (например, локальная модель недоступна), запрос не уходит «куда получится». Цель понижается до L1 (§6.2 архитектуры).

**Изменение профиля:**

| Изменение | Кто | Согласование | Когда вступает в силу |
|---|---|---|---|
| Сужение: `hybrid` → `local-only` или `off`, отказ от провайдера | Владелец сервиса или команды | Не требуется (безопасное направление) | Сразу, включая текущие инциденты |
| Расширение: `local-only` → `hybrid`, выбор другого провайдера | Владелец сервиса — инициатор | Security (класс данных и провайдер) + SRE-лид (eval), четыре глаза | Для новых инцидентов; текущие дорабатывают на прежнем профиле |
| Смена модели внутри профиля | Владелец сервиса — инициатор | SRE-лид: модель должна пройти eval (ниже) | Для новых инцидентов |
| Добавление провайдера или модели в реестр | Оператор платформы | Security — A, четыре глаза | После прохождения eval и red-team |

Агент не может менять профили и реестр — это такие же объекты политики, как уровни автономности.

**Профиль и автономность.** Качество агента зависит от модели, поэтому:

- каждая пара «модель + upstream-провайдер» проходит eval-контур по golden-набору; профиль нельзя выбрать с моделью без пройденного eval;
- уровни автономности и статистика повышения (§4.5 архитектуры) привязаны к профилю, на котором они набраны. После смены профиля или модели в сторону расширения уровни по затронутым классам понижаются до L1 и снова набираются по данным. Сужение до `local-only` уровни тоже понижает, если локальная модель не прошла eval на этих классах;
- в decision record пишутся профиль, backend, модель и фактический upstream-провайдер.

**Интерфейс.** Профиль выбирается в UI/CLI Control Plane (`aegisops llm profile set …`), но хранится как код в Git. UI создаёт PR, а сужение применяется сразу и фиксируется коммитом задним числом. На карточках L1/L2 видно, какой backend сформировал рекомендацию.

### 1.3 MVP: только OpenRouter

В MVP (MVP-A и MVP-B, [plan-mvp.md](../01-planning/plan-mvp.md)) реестр содержит **один backend — OpenRouter**. Локальные модели и выбор профиля пользователями появляются после MVP.

| Что | В MVP | После MVP |
|---|---|---|
| Реестр | Только `openrouter`: модель GLM 5.3 Flash (`z-ai/glm-5.3-flash-20260826`) у провайдера Inceptron (endpoint `inceptron/fp8`), резерв — Wafer (`wafer/us`) (§1.4) | Локальные модели, другие провайдеры |
| Профили | Один профиль организации: `hybrid` без локального backend'а. Сервис может только сузить его до `off` | `local-only` / `hybrid` / `off` на уровнях организации, команды и сервиса (§1.2) |
| restricted и ПДн граждан РФ | **Не попадают в контекст LLM вообще.** Агент видит только разрешённые части инцидента; в decision record помечается, что часть контекста исключена | Обрабатываются локальной моделью в юрисдикции данных |
| confidential с возможными ПДн (логи, трейсы, тикеты) | Не отправляются по умолчанию. Источник включается отдельно: подтверждено отсутствие ПДн или пройдены маскирование (§5) и юридическое согласование (§4.2). **В коде закреплено `dataclass.ConfidentialExternalAvailable = false`**: пока нет NER для ФИО, включить confidential для внешнего LLM нельзя, `NewRegistry` такой источник отвергает, а `audit.Validate` не принимает запись `sent` с классом confidential | То же, плюс локальная обработка для невключённых источников |
| Маскирование | Без LLM: правила, шаблоны с контрольными суммами и локальная NER-библиотека (не генеративная модель) | Плюс `local-small` |
| Недоступность OpenRouter | Inceptron недоступен → Wafer. Недоступны оба или сам OpenRouter → новых предложений нет, цели с L2 переходят в L1 (CH-A13) | Плюс fallback на `local-large` |

**Что реально видит LLM в MVP**, если сервисы обрабатывают ПДн граждан РФ: метрики и алерты, топологию и service graph, события деплоев и Kubernetes, агрегаты СУБД (сессии по состояниям, `SHOW POOLS`), нормализованные запросы `pg_stat_statements` (после включения источника), манифесты и runbook'и. Логи и трейсы приложений — только из источников, включённых по правилам выше.

Это осознанное ограничение: качество диагноза для классов, где решающая улика лежит в логах приложения, может не дотянуть до G0. Такие классы остаются на L0. Это сигнал, что следующим шагом после MVP нужна локальная модель, а не повод ослабить правила классов.

### 1.4 Выбранная модель для MVP

Модель: Z.ai GLM 5.3 Flash, slug `z-ai/glm-5.3-flash-20260826` (релиз 26.08.2026). Данные — API OpenRouter на 05.11.2026, цены и доступность могут меняться.

**Решение 06.11.2026:** основной endpoint — **Inceptron fp8**, резервный — **Wafer**; Open Inference fp4 выведен из эксплуатации. Основание — eval на `probe` (480 кейсов, промпт v2, 05.11.2026):

| | Inceptron fp8 (основной) | Wafer nvfp4 (резерв) | Open Inference fp4 (выведен) |
|---|---|---|---|
| Совпадение первопричины | 100% [99,2; 100] | 100% [99,2; 100] | 87,9% [84,7; 90,5] |
| Допустимость действия | 100% [99,2; 100] | 98,8% [97,3; 99,4] | 91,2% [88,4; 93,5] |
| Вредные действия | 0% | 0% | 3,5% |
| Обрезанные ответы (зацикливание) | 0 | 0 | 11 |
| Медиана / p90 задержки | 8,9 / 15,4 с | 4,8 / 7,7 с | 9,3 / 13,5 с |
| Стоимость прогона `probe` | $0,48 | $0,12 | $0,21 |

Парный тест Макнемара по допустимости действия: Inceptron против Open Inference — 42 : 0 (p ≈ 5·10⁻¹³), Wafer против Open Inference — 41 : 5 (p ≈ 4·10⁻⁸), Inceptron против Wafer — 6 : 0 (p ≈ 0,03). Отставание Open Inference от обоих (8,8 и 7,6 п. п.) больше утверждённого зазора 5 п. п.; Wafer отстаёт от Inceptron на 1,2 п. п. — в пределах зазора, поэтому уровни автономности при переключении на резерв сохраняются. Все 6 ошибок Wafer — в осторожную сторону (`none` / `recommend` вместо увеличения пула или действие без параметра), без вредных действий. Результат синтетики для fp8 упирается в потолок: реальное качество покажут реальный golden-набор и shadow.

| Параметр | Основной: Inceptron | Резервный: Wafer |
|---|---|---|
| Endpoint | `inceptron/fp8` | `wafer/us` |
| ZDR (список `/api/v1/endpoints/zdr`) | Да | Да |
| Квантование | fp8 | nvfp4 |
| Контекст / максимум вывода | 1 048 576 / 943 718 токенов | 1 048 576 / 196 608 токенов |
| Structured outputs, tools, seed | Да | Да |
| Цена за 1M токенов: вход / выход | $0,15 / $0,45 | $0,037 / $0,184 |
| Доступность за сутки на момент проверки | 99,93% | 100% |
| Имя провайдера в ответе OpenRouter | `Inceptron` | `Wafer` |
| Регион обработки | **Не подтверждён.** По одному источнику — ЕС; запросить у OpenRouter вместе со списком субпроцессоров | US (по тегу endpoint'а) |

Inceptron — один из четырёх fp8-endpoint'ов GLM 5.3 Flash, у которых одновременно есть ZDR, structured outputs и seed (ещё Morph, Near AI, Tenstorrent); у Z.AI нет structured outputs, у BaseTen — seed.

У Wafer есть второй endpoint, `wafer/nvfp4`, тоже с ZDR, но дороже ($0,054 / $0,20) и без указанного региона. Если OpenRouter не позволяет закрепить конкретный endpoint по тегу, закрепляются провайдер `wafer` и квантование nvfp4: оба endpoint'а Wafer в nvfp4. Фактический тег всё равно пишется в decision record.

**Что учесть:**

- **Смена основного endpoint'а сделана до shadow**, как и планировалось: после старта shadow это была бы новая модель и новая статистика G0. Решение принято 06.11.2026; по RACI изменение реестра требует подтверждения security (четыре глаза).
- **Резерв переключает роутер Aegis, а не OpenRouter.** Встроенный fallback OpenRouter выключен (`allow_fallbacks: false`): он выбирал бы провайдера по каждому запросу, и один инцидент мог бы смешать ответы разных endpoint'ов. Роутер Aegis переключается на Wafer по health-check или после **3 неудачных HTTP-попыток (ошибок или таймаутов) подряд** — считаются попытки, а не вызовы роутера *(утверждено 05.11.2026; уточнено 07.11.2026, см. architecture.md §6.2)* и возвращается на основной endpoint с гистерезисом — **10 минут стабильных health-check'ов** *(утверждено 05.11.2026)*. Инцидент, начатый на одном endpoint'е, продолжается на нём, пока тот доступен. Каждое переключение пишется в аудит.
- **Wafer — это другая модель для eval.** nvfp4 и fp8 — разные форматы квантования, и ответы различаются. Wafer проходит собственный eval на том же golden-наборе.
- **Уровни автономности на резерве.** Уровни, набранные на основном endpoint'е, действуют на Wafer, только если его eval не хуже основного больше чем на допустимый зазор — **5 п. п. по совпадению диагноза и допустимости действия** *(утверждено 05.11.2026)*. Иначе на время работы через Wafer цели переходят в L1: рекомендации есть, автономного исполнения нет. Кейсы, обработанные через Wafer, помечаются в статистике G0 и G1 отдельно.
- **Недоступны оба** endpoint'а или сам OpenRouter → новых предложений нет, цели с L2 переходят в L1 (CH-A13).
- **Structured outputs обязательны.** Ответ модели валидируется по схеме (действие каталога и параметры). Это защита от prompt injection (§3 архитектуры), а не просто удобство.
- **Юрисдикция может различаться.** Wafer обрабатывает данные в США, регион Inceptron не подтверждён (возможно, ЕС). Если основной и резервный endpoint'ы в разных юрисдикциях, переключение на резерв меняет правовую схему передачи: оценка передачи по GDPR и DPIA должны покрывать обе. Регионы нужно закрепить документально: в DPA с OpenRouter, в списке субпроцессоров и в записи DPIA о потоке данных. Для данных граждан РФ ничего не меняется: в OpenRouter они не уходят (§4.2).

## 2. Классы данных

| Класс | Что относится | Внешний LLM | Маскирование до отправки | Хранение промптов и ответов *(предложение)* |
|---|---|---|---|---|
| **public** | Документация вендоров, открытые зависимости и их CVE, публичные runbook'и | Да | Не требуется | 90 дней в трассах |
| **internal** | Метрики и их метки без идентификаторов пользователей; имена сервисов, топология, service graph; алерты; манифесты и IaC без секретов; внутренние runbook'и | Да | Сканер секретов обязателен | 90 дней в трассах |
| **confidential** | Проприетарный исходный код; логи и трейсы приложений; тексты PR, тикетов и постмортемов; планы запросов и статистика СУБД без значений из строк | Только после маскирования и при условиях §4; иначе только локально | Обязательно, с проверкой (§5) | 30 дней, только в маскированном виде |
| **restricted** | Немаскированные персональные данные; содержимое строк БД и результаты запросов к пользовательским таблицам; тела HTTP-запросов и payload'ы eBPF; платёжные данные; данные, локализованные по 152-ФЗ, вне маскирования | Нет, только `local-large` / `local-small` в своей юрисдикции | Нет: данные не покидают контур | Не хранятся вне инцидента; в decision record — только хеши и ID |
| **секреты** | Ключи, токены, пароли, cookies, заголовки `Authorization`, строки подключения | Нет, ни в какую модель | Вырезаются целиком | Не хранятся |

## 3. Правила классификации

1. **Класс по источнику по умолчанию.** Каждый источник в intake получает класс по умолчанию:

   | Источник | Класс по умолчанию |
   |---|---|
   | Метрики Prometheus/Mimir | internal |
   | Алерты Alertmanager, PagerDuty, Opsgenie | internal |
   | Логи Loki/ClickHouse | confidential |
   | Трейсы Tempo (атрибуты span'ов) | confidential |
   | Payload'ы eBPF, тела запросов | restricted |
   | `pg_stat_activity.query`, логи медленных запросов PostgreSQL | restricted (в тексте запроса бывают литералы с ПДн) |
   | `pg_stat_statements` (нормализованные запросы) | confidential |
   | Исходный код, PR, тикеты, постмортемы | confidential |
   | Манифесты, Helm, IaC (сюда же PDB) | internal, после сканера секретов: маскировщик вызывается для каждого internal-фрагмента |
   | События Kubernetes и деплоев, статус rollout (§1.3) | internal |
   | Топология: сервис, автоскейлер, поды (§2) | internal |
   | Агрегаты СУБД: сессии по состояниям, `SHOW POOLS`, параметры пула (§1.3) | internal |
   | Каталог допустимых действий (`allowed_actions`, генерирует платформа) и runbook'и | internal |

   Реестр источников MVP — `dataclass.MVPRegistry`. Источники, где возможны ПДн граждан РФ (логи, трейсы, тикеты, постмортемы), помечены `MayContainPersonalDataRU`: наружу они не уходят независимо от класса.

2. **Неизвестный источник → restricted** (fail-closed), пока владелец не назначит класс.
3. **Смешанный контекст получает максимальный класс** из его частей. Роутер не разбивает один промпт между моделями разных классов.
4. **Сбой маскирования → restricted.** Ошибка, таймаут или низкая уверенность маскировщика переводят фрагмент в restricted. Источник запрещённого класса до маскировщика не доходит вообще.
5. **Повышение класса** — автоматическое (детектор нашёл ПДн во внешне-разрешённом фрагменте). В MVP гражданство субъекта по данным не определить, поэтому любые найденные ПДн повышают фрагмент до restricted (`dataclass.Escalate`) *(утверждено 07.11.2026)*. Не confidential: гражданство субъекта в MVP не определяется, поэтому любая находка считается возможными ПДн граждан РФ (§4.2). Контракт для детекторов маскировщика (часть 2): о каждой найденной ПДн сообщать `CategoryPersonal` с `Count > 0` — и когда значение заменено псевдонимом, и когда нет. Классом детектор не управляет. Следствие для MVP: маскирование ПДн не делает фрагмент отправляемым, псевдонимы §5.1 нужны для локальных моделей и для этапа после включения confidential. Фрагмент исключается из запроса, а исключение записывается в decision record (`llm.excluded_fragments` с причиной `personal_data`). Исключённый обязательный фрагмент — запроса нет (`llm.reason = required_excluded`). **Понижение** — только человеком, через изменение политики по принципу четырёх глаз.
6. Класс записывается в decision record вместе с маршрутом (какая модель, какая юрисдикция).

## 4. Требования 152-ФЗ и GDPR

### 4.1 Что из них следует для платформы

| Требование | 152-ФЗ (РФ) | GDPR (ЕС) | Что делает платформа |
|---|---|---|---|
| Локализация | Запись, систематизация, накопление и хранение ПДн граждан РФ — в базах данных на территории РФ (ст. 18 ч. 5) | Прямой локализации нет; ограничена передача за пределы ЕЭЗ (гл. V) | Хранилища логов, трейсов, Qdrant и трасс LLM для данных граждан РФ размещаются в РФ, для данных из ЕС — в ЕС или по правилам гл. V |
| Трансграничная передача | Требует уведомления Роскомнадзора до начала передачи и проверки страны получателя (ст. 12) | Нужен механизм передачи (решение об адекватности, SCC) и DPA с обработчиком (ст. 28) | OpenRouter (США) — трансграничная передача и для РФ, и для ЕС. По GDPR у OpenRouter есть DPA (OpenRouter — processor) со стандартными договорными условиями (SCC 2021), но DPA нужно подписать и проверить список субпроцессоров: upstream-провайдеры тоже обработчики. По 152-ФЗ США не относятся к странам с адекватной защитой ПДн (проверить юристам), поэтому ПДн граждан РФ в OpenRouter не отправляются ни в каком виде (п. 4.2) |
| Оценка рисков | Модель угроз и уровень защищённости ИСПДн | DPIA (ст. 35) | DPIA и модель угроз ИСПДн — часть Этапа −1 |
| Утечки | Уведомление Роскомнадзора: первичное в течение 24 часов, итоговое — 72 часов | Уведомление надзорного органа в течение 72 часов (ст. 33) | Утечка данных за границу класса — инцидент безопасности со своим runbook'ом и уведомлением DPO |
| Минимизация | Обработка в пределах заявленных целей | Data minimisation (ст. 5) | В LLM уходит только контекст, нужный для диагноза; содержимое строк БД не извлекается |

### 4.2 Маскирование — не обезличивание

Псевдонимизированные данные по GDPR остаются персональными (Recital 26). Обезличивание по 152-ФЗ тоже имеет формальные требования. Поэтому:

- **По умолчанию** confidential-данные, которые могут содержать ПДн (логи, трейсы, тикеты), обрабатываются **локально**, даже после маскирования.
- Отправка маскированного confidential во внешний LLM включается **по каждому источнику отдельно**. Условия: юристы подтвердили основание (DPA, SCC, уведомление Роскомнадзора), DPIA покрывает этот поток, маскировщик прошёл проверки §5 на данных этого источника.
- Для исходного кода и IaC без ПДн OpenRouter допускается после сканера секретов, с настройками §1.1 (ZDR, `data_collection: deny`, закреплённые провайдеры).
- **Данные, которые могут содержать ПДн граждан РФ, в OpenRouter не уходят даже маскированными.** Для них маршрут всегда локальный (`local-large` в РФ), пока юристы не оформят основание для передачи в США.

### 4.3 Юрисдикция локальных моделей

«Локальная модель» — это модель, развёрнутая **в той же юрисдикции, что и данные**. Для данных граждан РФ это инференс в РФ. Для данных из ЕС — в ЕС. Если у платформы контуры в обеих юрисдикциях, роутер выбирает инстанс по метке юрисдикции источника. Эта метка обязательна для каждого источника в intake.

## 5. Маскирование

### 5.1 Что маскируется

| Сущность | Способ обнаружения | Замена |
|---|---|---|
| ФИО, email, телефон | NER (после MVP — `local-small`) + регулярные выражения; в MVP NER нет — только правила, см. «Реализация» | Псевдоним `<PERSON_7f3a>` |
| Паспорт, СНИЛС, ИНН, номера документов ЕС | Шаблоны с контрольными суммами (у паспорта РФ суммы нет — по ключевому слову) | `<DOC_…>` |
| Номера карт | Шаблон + проверка Луна | `<CARD>` |
| IP-адреса клиентов | Шаблон; внутренние подсети из allowlist не маскируются | `<IP_…>` |
| ID пользователей, заказов, логины | Не маскируются: идентификаторы ПДн не считаются *(решение 07.11.2026)*; email или ФИО в значении находят общие детекторы | — |
| ID сессий | Правила по именам полей (`session`, `session_id`, `sid`): bearer-креденшл, обрабатывается как секрет *(решение 07.11.2026)* | `<SECRET_REMOVED>` |
| Литералы в SQL | Нормализация запроса (как в `pg_stat_statements`) | `$1`, `$2` |
| Секреты | Правила gitleaks/trufflehog + энтропия | Фрагмент вырезается, остаётся `<SECRET_REMOVED>` |

В MVP любая находка ПДн исключает фрагмент из запроса во внешний LLM (§3 п. 5).

Псевдонимы детерминированы внутри одного инцидента (соль на инцидент): LLM видит, что `<PERSON_12>` встречается в трёх логах, но не видит сам email. Таблица соответствий хранится только локально и удаляется вместе с данными инцидента (в MVP не хранится вовсе: псевдонимы воспроизводятся по HMAC, см. «Реализация»).

#### Реализация (Этап 0a)

Код — `internal/masker`: детерминированные правила без LLM и внешних библиотек (regexp RE2, контрольные суммы, `net/netip`). Версия правил `aegis-rules/<версия>+cfg.<хэш списка внутренних сетей>` попадает в decision record. Любые сбои — ошибка (роутер → `masker_failure`).

- **Секреты:** подмножество правил gitleaks (PEM, токены облаков и git-хостингов, JWT, заголовки `Authorization`/`Cookie`, `user:pass@` в URL, присваивания `password=…`/`?token=…&sig=…`), имена полей (`password`, `*_token`, `session_id`/`sid`…), `Secret.data` k8s и пары `{name: DB_PASSWORD, value: …}`, энтропийное правило: ≥ 32 символа, заглавные, строчные и цифры, энтропия Шеннона ≥ 4.1; исключены только-hex строки и идентификаторы из слов — CamelCase-имена алертов, метрик и классов с цифрами (`HighRequestLatencyP99ThresholdExceeded5m`) *(правила 1.1.0, 07.11.2026)*. Вырезается значение, остальной текст остаётся *(предложение)*. Секрет в ключе объекта — ошибка (fail-closed).
- **ПДн:** email, телефон, карты (Luhn), СНИЛС, ИНН, IBAN (mod-97), паспорт РФ, IPv4/IPv6, ФИО, поля `phone`/`email`/`inn`…. Идентификаторы (`user_id`, `customer_id`, `order_id`, `login`, `username`…) ПДн не считаются и не маскируются *(решение 07.11.2026, правила 1.2.0)*. ИНН и паспорт (у паспорта РФ контрольной суммы нет) и «голый» СНИЛС распознаются только с ключевым словом слева, иначе 10-значное число (например, epoch) неотличимо от ИНН *(предложение)*. Национальные номера документов ЕС, кроме IBAN, — отложены *(предложение)*.
- **ФИО без NER** *(предложение)*: только кириллица с отчеством («Фамилия Имя Отчество», «Имя Отчество») и «Фамилия И. О.»; латиница и имена без отчества не находятся — поэтому `ConfidentialExternalAvailable` остаётся `false`.
- **IP:** адреса из allowlist внутренних сетей не маскируются; по умолчанию 10/8, 172.16/12, 192.168/16, 100.64/10, 127/8, 169.254/16, fc00::/7, fe80::/10, ::1 *(предложение)*.
- **SQL-литералы** (`$1`) не реализованы: SQL-источники до маскировщика в MVP не доходят по гейту.
- **Категории:** только `secret` и `personal_data`; карты, IP и документы — тоже `personal_data` (итог тот же — restricted).
- **Числа:** не переписываются, кроме значений под ПДн-полями (`phone`, `inn`…) и целых из 13–19 цифр, проходящих Luhn с первой цифрой 2–6, — они становятся строкой `<CARD>`. Дробные, `bool` и `null` не трогаются.
- **Ключи объектов** сканируются теми же детекторами: ПДн в ключе — ключ заменяется псевдонимом (совпадение ключей после замены — ошибка); секрет в ключе — ошибка (вырезать нельзя, fail-closed).
- **Идемпотентность:** собственные заглушки (`<SECRET_REMOVED>`, `<CARD>`, `<PERSON_…>`…) и шаблонные значения (`${…}`, `{{…}}`, `$(…)`, `***`, `xxx`, пустая строка) находками не считаются; повторное маскирование ничего не меняет.
- **Конфигурация:** `masker.New(Config{PseudonymKey, InternalNets})`; без `IncidentID` во фрагменте маскирование — ошибка (не из чего вывести ключ инцидента). Любая правка правил поднимает `masker.RulesVersion` (сейчас 1.2.0).
- **Псевдонимы** *(предложение)*: `<PERSON_xxxxxxxx>`, `<DOC_…>`, `<IP_…>` — 8 hex от HMAC-SHA256 с ключом инцидента `HMAC(мастер-ключ, IncidentID)`; нормализация (телефон — цифры, email — нижний регистр). Таблица соответствий не хранится: восстановление в MVP не нужно, повторяемость даёт HMAC; локальное хранилище станет актуальным с локальными моделями. Мастер-ключ — файл `AEGIS_MASKER_KEY_FILE` (hex, ≥ 32 байт). Карты — `<CARD>` без хэша.
- **Пределы** *(предложение)*: 8 MiB строк и ключей на фрагмент, вложенность 512; сверх — ошибка. Строки больше 32 KiB сканируются окнами по 16 KiB с перекрытием 2 KiB (regexp не прерывается по ctx, а таймаут роутера — 2 с), ctx проверяется между окнами; PEM ищется по всей строке с проверкой ctx. Остаточный риск: токен длиннее ~2 KiB без пробелов на границе окна может быть вырезан не целиком.
- **Известные пропуски** (кандидаты в корпус §5.2): СНИЛС с пробелами (`123 456 789 01`), ключевое слово вплотную к числу (`ИНН7701…`), карта группами 8+8, телефон `7XXXXXXXXXX` без `+`, ФИО латиницей, в верхнем регистре или без отчества, `curl -u user:pass`, `api-key VALUE` без `:`/`=`. Ложные срабатывания: `token: expired` в прозе вырезает слово `expired`; `1.2.3.4` без `v` считается публичным IP.

### 5.2 Проверка маскирования

- **Тестовый корпус:** синтетические логи, трейсы и тикеты с внедрёнными ПДн и секретами, по каждому источнику из §3. *Ещё не создан;* пока есть модульные тесты `internal/masker` (каждое правило, ложные срабатывания, свойства, fuzz) и проверка, что на всём корпусе eval (`eval/golden-synthetic/data`) маскировщик ничего не находит.
- **Пороги *(предложение)*:** recall по ПДн ≥ 99% на корпусе; по секретам — 100%, любой пропуск блокирует выкатку маскировщика.
- **Canary-секреты:** в staging-логи регулярно подбрасываются фиктивные секреты и ПДн с уникальными маркерами. Egress-прокси ищет маркеры в исходящем трафике к внешнему LLM. Одно совпадение — это инцидент безопасности и автоматический перевод источника в restricted.
- Регрессионный прогон корпуса — при смене маскировщика, NER-модели или формата логов источника.

## 6. Контроль на выходе

- Во внешний LLM можно попасть **только через роутер**. Для остальных компонентов egress к провайдерам запрещён сетевой политикой.
- Роутер пишет в аудит хеш отправленного промпта, класс, источник, юрисдикцию и маршрут.
- **Egress закрыт по умолчанию** для всех компонентов Control Plane (NetworkPolicy). Egress-прокси пропускает `openrouter.ai` только для identity роутера ([threat-model.md](threat-model.md) T-17).
- **Трассы рассуждений LLM** (Langfuse или OTel GenAI) — только self-hosted, в юрисдикции данных: в них лежит контекст инцидента. Облачные версии сервисов трассировки не используются.
- **Метки метрик:** в контекст попадают только метки из allowlist, значения проверяются шаблоном, свободные значения отбрасываются (T-04). Allowlist MVP — `dataclass.MVPLabelPolicy`: `service`, `namespace`, `pod`, `container`, `deployment`, `database`, `cluster`, `topic` (имя в стиле DNS), `limit_mb` (до 7 цифр), `source` (короткий идентификатор).
- **Slack — тоже граница выхода данных.** Это внешний SaaS за пределами РФ, поэтому в карточках только данные не выше класса internal, без ПДн граждан РФ. Детерминированные фрагменты-доказательства в карточках проходят тот же маскировщик, что и запросы к LLM (T-09).
- Квоты и токен-бюджеты действуют на инцидент и на период (§6.2): 200 000 токенов на инцидент и 2 000 000 токенов на сервис за сутки UTC *(предложение)*. Превышение переводит запросы в локальную модель; в MVP, без локальной модели, — понижение цели до L1. Счета хранятся персистентно (`internal/routerstate`): рестарт процесса их не обнуляет, удаление хранилища останавливает роутер до ручного `Resume`.
- **Потолок контекста одного запроса — 64k токенов** *(утверждено 05.11.2026)*, хотя модель принимает до 1M. При превышении роутер отбрасывает наименее релевантные фрагменты и помечает это в decision record ([threat-model.md](threat-model.md), T-15).
