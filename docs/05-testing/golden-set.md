# Golden-набор: синтетическая часть

> Основа — [architecture.md](../00-overview/architecture.md) §6.3 (eval-контур, ежедневная eval-проба). Код и данные — `eval/golden-synthetic/` в корне проекта. Описание набора ведётся в этом файле.
>
> Статус: **версия 2.0.0 (формат ответа v2), сгенерирована 06.11.2026**; версия 1.0.0 (формат v1, 05.11.2026) хранится и воспроизводится (`generate.py --format v1`). Данные синтетические, без ПДн, класс internal: набор можно отправлять в OpenRouter до подписания DPA ([data-classes.md](../02-security/data-classes.md)).

## 1. Зачем и где границы

Синтетический набор нужен для трёх задач:

1. **Ежедневная eval-проба** — ловит тихую смену модели у провайдера ([threat-model.md](../02-security/threat-model.md) T-12).
2. **Сравнение endpoint'ов** до старта shadow: Open Inference (fp4), Wafer (nvfp4) и Inceptron (fp8). Выполнено 05.11.2026, итоги — §9.
3. **Регрессионный прогон** при смене промпта, каталога или модели.

Чего синтетический набор **не** делает:

- **Не измеряет реальное качество диагноза.** Кейсы построены по тем же правилам runbook'ов, что и промпт. Хороший результат на нём значит «модель следует runbook'ам и устойчива к ловушкам», а не «модель хорошо диагностирует реальные инциденты». Gate G0 считается только по реальным кейсам shadow.
- **Не заменяет red-team.** Слайс `adversarial` проверяет устойчивость *модели* к инъекциям в полях, которые до неё доходят. Проверки *конвейера* (вырезание SQL-комментариев, allowlist меток и т. п.) — это RT-01…RT-17.

## 2. Состав

Набор `probe` — **480 кейсов**. Этого достаточно, чтобы граница 3σ ежедневной пробы была ≈ 5 п. п. (§6.3 архитектуры).

| Класс | Варианты | Кейсов |
|---|---|---|
| RB-001 Насыщение пула PgBouncer | пул мал (60), утечка в клиенте (30), медленные запросы (15), инъекции на базе RB-001 | 125 |
| RB-002 Исчерпание `max_connections` | нет запаса для увеличения пула (15) | 15 |
| RB-003 Деградация после релиза | canary (45), bake (25), недостаточно данных × 3 политики (25), подделка метрик приложения (10), рост CPU после релиза (10), инъекции на базе RB-003 | 122 |
| RB-006 Нехватка capacity | рост нагрузки (45), отставание очереди KEDA (25), достигнут `maxReplicas` (25), спайк уже прошёл (15), инъекции на базе RB-006 | 123 |
| RB-004 CrashLoopBackOff | после релиза (20), без релиза (10) | 30 |
| RB-005 Утечка памяти | один под или все поды (30) | 30 |
| RB-007 Избыточная capacity | 20 | 20 |
| other | деградация из-за СУБД, не из-за релиза (15) | 15 |

Точные числа по классам и слайсам — в `data/manifest.json`.

**Слайсы** — срезы, по которым считаются метрики отдельно:

| Слайс | Кейсов | Что проверяет |
|---|---|---|
| `core` | 200 | Основные сценарии трёх классов первого shadow: правильное действие с правильными параметрами |
| `negative` | 100 | Похоже на основной сценарий, но правильно *не* делать очевидного: не увеличивать пул при утечке, не масштабировать при `maxReplicas`, не реагировать на прошедший спайк |
| `confuser` | 105 | Соседние классы с похожими симптомами: рост CPU после релиза — это регрессия, а не нехватка capacity; crashloop лечится откатом, а не рестартом |
| `insufficient` | 25 | Canary без достаточной выборки: решение по политике сервиса (`hold` / `rollback` / `human`) |
| `adversarial` | 50 | Инъекции в тексте алерта (40) и подделка метрик самим приложением (10): ответ должен совпадать с ответом без инъекции |

Набор `dev` (113 кейсов, другой seed) — для отладки промптов. На `probe` промпт не подбирают, иначе проба перестанет быть независимой.

## 3. Кейс

Модели отправляется только поле `input`. Остальные поля содержат ответ:

| Поле | Содержимое |
|---|---|
| `input.alert` | Алерт: имя, severity, метки, аннотации (в слайсе `adversarial` — с инъекцией) |
| `input.service` | Сервис, autoscaler (HPA или ScaledObject, `min` / `max` / текущие реплики), политика для недостаточных данных; список подов цели `pods` (с v3) |
| `input.metrics` | Временные ряды за 30 минут с шагом в минуту: ingress, PgBouncer, PostgreSQL, CPU, память, отставание Kafka, метрики приложения с пометкой `self_reported` |
| `input.db` | Агрегаты СУБД: `SHOW POOLS`, сессии по состояниям (как от функции-агрегата), `max_connections` и запас |
| `input.rollout` | Состояние Argo Rollout и вердикт статистического гейта |
| `input.deploys`, `input.k8s_events` | Только структурированные поля: ревизия, digest образа, время, reason события |
| `input.allowed_actions` | Действия каталога, доступные для цели. В формате v2: в `params` — только дискретные параметры, которые выбирает модель (`scope`, `pod_name`, `reason`, `parameter`); в `computed` — величина и идентификаторы, вычисленные правилом шага каталога (`new_pool_size`, `new_min_replicas`, `value`, `database`, `analysis_run`). В формате v1 — границы параметров, величину выбирала модель |
| `expected` | Класс, первопричина, допустимые действия с ограничениями параметров, вредные действия |

Средний размер входа — около 3,6 тыс. символов (≈ 1,2–1,5 тыс. токенов), максимум — около 8 тыс. символов. Это далеко от потолка контекста 64k.

## 4. Метрики

`score.py` считает метрики по классам, слайсам и в целом, с 95%-ми ДИ Уилсона:

| Метрика | Смысл | Связь с документами |
|---|---|---|
| `root_cause_match` | Совпала первопричина | «Совпадение диагноза» (G0, eval-проба) |
| `class_match` | Совпал класс инцидента | Вспомогательная |
| `admissible` | Действие в списке допустимых, параметры в границах | «Допустимость действия» (G0, зазор 5 п. п. между endpoint'ами) |
| `harmful` | Выбрано действие из списка вредных для кейса | «Вредные предложения» |
| `schema_valid` | Ответ прошёл проверку схемы | Работа structured outputs |
| `decision_agreement` | Совпали первопричина и тип действия с эталонным ответом этой же модели | Основная метрика совпадения eval-пробы (§6.3 архитектуры) |
| `agreement` | Действие и все параметры совпали с эталонным ответом | Вспомогательная |

**Эталонные ответы** для `agreement` фиксируются в начале калибровки на каждом endpoint'е, с фиксированными параметрами генерации (температура 0, seed, если провайдер его поддерживает). Их файлы хранятся рядом с отчётами калибровки и замораживаются вместе с базой.

## 5. Контроль версий

- Набор однозначно определяется версией генератора, версией набора (`--format v1|v2|v3`), seed'ом и SHA-256 из `data/manifest.json`; прежние версии наборов, промптов и схем — в `sets_history`, `prompt_history`, `answer_schema_history`. Кейсы v1 и v2 одинаковы во всём, кроме `allowed_actions` и `expected`; кейсы v2 и v3 — во всём, кроме `input.service.pods` и `generator_version`. Версии наборов: v1 (формат ответа v1, до 06.11.2026), v2 (формат ответа v2, 06–07.11.2026), v3 (формат ответа v2 + поды цели во входе, с 07.11.2026, см. §13); записи прежних версий — в `sets_history`. Смена набора — новые эталоны и калибровка с нуля; состояние калибровки хранится по версии набора. Повторная генерация с теми же параметрами даёт тот же хеш — это проверяет `selftest.py`.
- В manifest также записаны хеши промпта (`prompt/system-v1.md`) и схемы ответа. Смена любого из них — это смена golden-набора или промпта: замороженная база ежедневной пробы пересчитывается только по утверждённому изменению (§6.3 архитектуры).
- Изменения генератора — через PR с ревью SRE-лида; новая версия набора получает новый файл (`probe-v3.jsonl`), старые не перезаписываются.

## 6. Стоимость прогона

Промпт ≈ 1,2 тыс. токенов плюс вход ≈ 1,3 тыс. — около 2,5 тыс. входных токенов на кейс, то есть ≈ 1,2M токенов на прогон 480 кейсов. Выход зависит от объёма reasoning, обычно 0,3–1 тыс. токенов на кейс. По ценам на 05.11.2026 это **≈ $0,1–0,3 в день на endpoint**, около $0,5 в день за ежедневную пробу обоих endpoint'ов и сравнение с fp8 на этапе выбора.

## 7. Как переходить на реальный golden-набор

1. После подписания DPA собирается реальный golden-набор из постмортемов (с учётом классов данных: confidential с ПДн в OpenRouter не уходит).
2. Синтетический `probe` остаётся для ежедневной пробы: он стабилен и не зависит от того, сколько реальных инцидентов набралось.
3. Реальный набор используется для eval перед shadow и при смене модели. Его база считается отдельно.
4. Если синтетику заменяют или расширяют, это смена golden-набора, и база ежедневной пробы пересчитывается.

## 11. Формат ответа v2 (06.11.2026)

**Решение:** модель выбирает только действие и дискретные параметры — какой под перезапустить (`scope`, `pod_name`), с какой причиной откатить (`reason`), какой параметр СУБД менять (`parameter`). Величину изменения и параметры-идентификаторы вычисляет детерминированное правило шага каталога ([action-catalog.md](../03-autonomy/action-catalog.md), поле `step`):

| Действие | Правило шага *(предложение)* |
|---|---|
| `workload.scale_out` | `min(границы, max(текущий min + 1, ⌈текущий min × 1,5⌉))` |
| `workload.scale_in` | `max(границы, min(текущий min − 1, ⌊текущий min × 0,75⌋))` |
| `pgbouncer.resize_pool` | `min(границы, max(пул + 1, ⌈пул × 1,25⌉))` |
| `postgres.set_restart_param` (`max_connections`) | `min(2 × текущее, ⌈текущее × 1,25⌉)`, подтверждает человек (L1) |

Значения правил всегда внутри границ v1, поэтому граница PEP остаётся вторым рубежом.

**Что изменилось в наборе:** `allowed_actions` показывает вычисленные значения в `computed`, ожидаемые ответы проверяют только тип действия и дискретные параметры. Схема ответа — `schema/answer.schema-v2.json`, промпт — `prompt/system-v3.md`. `score.py` и раннер поддерживают оба формата.

**Следствия:**
- Класс ошибок «параметр в границах, но не тот» исчезает; метрика допустимости действия на v2 выше, чем на v1, и с v1 напрямую не сравнивается.
- Проверка «всегда scale_out» в `selftest.py` на v2 даёт ≈ 15% допустимых (там, где scale_out и правда нужен), а не 0%: параметр больше не ловит плохую стратегию, её ловят тип действия и первопричина.
- Эталоны v1 (§10) для пробы не используются; нужны новые эталоны на `probe` v2 для Inceptron и Wafer.

## 12. Калибровка ежедневной пробы

Скрипт `eval/golden-synthetic/calibrate.py` реализует правила §6.3 архитектуры:

- `update` берёт новые полные прогоны `probe` профиля с тем же набором, промптом, схемой и параметрами генерации, что у эталона, считает метрики против эталона и добавляет точку в `calibration/<profile>-<set_tag>.json` (`set_tag` — имя файла набора без расширения, например `probe-v3`; состояние набора probe-v2 — архив в прежнем `calibration/<profile>.json`, не меняется). Нет эталона для текущего набора — вердикт ALERT (`no_reference`), код выхода 10, состояние не пишется;
- до заморозки базы: отклонение больше 5 п. п. от уровня эталона → DOWNGRADE (проба ≥ 460 кейсов);
- `freeze` (≥ 20 точек, по утверждению) фиксирует среднее и σ; дальше порог понижения = max(3σ, 1,5 п. п.), двусторонний; EWMA (λ = 0,2, L = 2,7) и две точки подряд за 2σ — ALERT; повторная заморозка только с `--force`;
- контролируются `decision_agreement` (основная), `root_cause_match`, `admissible`, `harmful`; доля обрезанных ответов — только ALERT.

Ежедневный запуск — облачная задача по расписанию (00:00 МСК): прогон `probe` на Inceptron и Wafer, `calibrate.py update`, коммит `runs/` и `calibration/` в ветку `probe-results` репозитория `limpjungle/aegis3311`.

## 13. Набор v3: поды цели во входе (07.11.2026, утверждено)

**Решение:** генератор пишет список подов цели в `input.service.pods`, модель его видит. Enum `pod_name` в `allowed_actions` сохраняется (в рабочей системе платформа тоже строит `allowed_actions` из состояния цели). Формат ответа (схема `answer.schema-v2.json`) и промпт (`system-v3.md`) не меняются: меняется одна переменная — вход. Seed'ы и RNG прежние, кейсы v3 совпадают с v2 во всём, кроме `input.service.pods` и `generator_version`.

**Причина:** кросс-проверка Go (`internal/step`) для `workload.restart` была частично тавтологичной — единственным источником имён подов служил enum из самого `allowed_actions`. Теперь Go берёт поды из `input.service.pods`, сам вычисляет доступность restart и сравнивает с `allowed_actions`; нет поля — ошибка (набор старше v3).

**Последствия:**
- новые эталоны на `probe` v3 для Inceptron и Wafer (≈ $0,55 на оба), записываются до пуша набора в main;
- калибровка начинается с нуля; freeze — не раньше 20-го ежедневного прогона на v3;
- метрики v3 могут отличаться от v2, напрямую их не сравнивать;
- до записи эталонов `calibrate.py update` выдаёт ALERT (`no_reference`, код 10) и не пишет состояние.
