# Глоссарий AegisOps AI

> Часть I Базы знаний. Структура документации и быстрый старт — в [README](../README.md).

## 1. Общие термины платформы

| Термин | Определение |
|---|---|
| **AegisOps AI** | Платформа автономной эксплуатации: от анализа кода до Day-2 операций в Cloud, Hybrid и Bare Metal |
| **Control Plane** | Центральный управляющий контур: UI/CLI, оркестрация, LLM-роутер, PDP, аудит, lease-менеджер. HA, минимум 3 домена отказа |
| **Cluster Agent** | Агент в целевом кластере: содержит PEP, исполнитель каталога действий, клиент lease'ов, локальный кэш политик и буфер аудита |
| **Домен отказа** | Зона доступности, стойка или площадка. Три разные площадки не обязательны, но мажоритарный кворум на двух площадках не переживает потерю одной |
| **Witness** | Третий узел кворума без полного набора данных, позволяющий двум площадкам сохранять кворум при потере одной |
| **Single-writer** | Принцип: анализ и чтение — active-active, любое изменяющее действие требует lease с fencing token на конкретную цель |
| **Fail-safe / Fail-closed** | При неопределённости система не продвигает изменение и не расширяет полномочия; при истечении lease или TTL политик агент переходит в read-only |
| **Blast radius** | Радиус поражения: сколько сервисов/данных пострадает от ошибочного действия |
| **Day-2** | Фаза эксплуатации после запуска: мониторинг, инциденты, самовосстановление, оптимизация |
| **Shadow Mode (L0)** | Режим наблюдения: агент читает реальные события prod и предлагает решения, которые сравниваются с действиями SRE. Ничего не исполняется |
| **Golden-набор** | Набор исторических инцидентов и синтетических сценариев с ожидаемыми диагнозами и допустимыми действиями для eval-контура |
| **Baseline** | Начальные значения метрик (MTTR и др.), собранные в shadow-фазе до внедрения, для сравнения «до/после» |
| **RAG** | Retrieval-Augmented Generation: подмешивание релевантного контекста (runbook'ов, постмортемов) в промпт LLM |
| **Sim-to-real gap** | Разрыв между симуляцией и реальностью: причина, по которой Digital Twin ограничен K8s-уровнем |

## 2. Модель автономности

| Термин | Определение |
|---|---|
| **L0 — Наблюдатель** | Ничего не исполняет; решения логируются и сравниваются с действиями людей. Обязательный стартовый уровень для каждого сервиса и класса действий |
| **L1 — Советник** | Рекомендация или карточка, применяет человек. Максимум для любых необратимых действий |
| **L2 — Оператор** | Действие применяется сразу после проверок, с уведомлением и окном отмены (5 минут). Только обратимые действия R1/R2 |
| **L3 — Автопилот** | Полностью автономно в рамках политик. Только действия каталога с проверенным откатом и постусловием; при провале постусловия — автоматический откат |
| **Класс обратимости R1** | Полностью обратимо: rollback деплоя, scale out. До L3 |
| **Класс обратимости R2** | Обратимо с издержками: рестарт, scale in, reload пула соединений. До L2, до L3 только по данным |
| **Класс обратимости R3** | Необратимо или риск потери данных: миграции схемы, удаление томов и OSD, рестарт СУБД. Не выше L1 |
| **Матрица автономности** | Таблица «действие × среда × обратимость», задающая потолок уровня. Хранится как политика; для одного действия уровень в prod не выше, чем в staging |
| **Автопонижение** | Срабатывание circuit breaker, инцидент по вине ИИ или высокая доля отмен снижают уровень на ступень без согласования |
| **Повышение по данным** | Кандидат: пройден shadow-период, N успешных исполнений без инцидентов, доля отмен ниже порога. Подтверждает SRE-лид, решение подписывается и пишется в аудит |
| **Error budget** | Бюджет ошибок сервиса по SLO; при исчерпании изменяющие действия замораживаются (остаются rollback и scale out) |
| **Circuit breaker** | M неудачных или отменённых действий подряд переводят цель в L1 |
| **Flapping** | Быстрое чередование состояний (например, scale out/scale in); защита — cooldown между повторами |
| **Окно отмены** | Период после применения L2-действия (по умолчанию 5 минут), в течение которого откат возможен одной кнопкой. Действие применяется сразу, окно — для отката, а не veto до исполнения. Для R2 откат может иметь издержки (например, повторный рестарт) |
| **Конкуренция с человеком** | Если человек взял инцидент (ack, ChatOps, ручное изменение), агент по этой цели переходит в L1 |

## 3. Каталог действий и политики

| Термин | Определение |
|---|---|
| **Каталог действий** | Версионируемый в Git реестр разрешённых операций: имя, схема параметров с границами, предусловия, постусловия, процедура отката, класс обратимости, допустимые цели, лимит частоты |
| **Предусловия** | Условия, которые должны выполняться до исполнения действия |
| **Постусловия** | Проверка успеха после исполнения; при провале — автоматический откат (для L3) |
| **PDP (Policy Decision Point)** | Точка принятия решения по политикам: OPA в Control Plane |
| **PEP (Policy Enforcement Point)** | Точка применения политик: проверка внутри каждого Cluster Agent непосредственно перед действием, в том числе офлайн по кэшу |
| **OPA (Open Policy Agent)** | Движок политик на Rego: политики действий агента (границы параметров, окна времени, запрещённые ресурсы) |
| **Kyverno / Gatekeeper** | Admission-контроллеры Kubernetes: лимиты ресурсов, запрет privileged, обязательные probes |
| **Policy bundle** | Подписанный, версионируемый пакет политик с TTL кэша и механизмом отзыва. Хранится как код, с тестами и ревью |
| **Принцип четырёх глаз** | Изменение политик и уровней автономности — только человеком, с подтверждением второго человека. Audit log не меняется вообще: он append-only (WORM) |
| **Kill switch** | Аварийная остановка: глобальный, на кластер, на класс действий. Доступен out-of-band; при срабатывании все агенты переходят в L1/read-only |
| **Dead-man's switch** | Отсутствие heartbeat агента или Control Plane — алерт людям (независимый мониторинг) |

## 4. Аренда и конкурентный доступ

| Термин | Определение |
|---|---|
| **Lease** | Аренда на изменение конкретной цели: один писатель на цель; выдаётся Control Plane |
| **Fencing token** | Монотонный номер, привязанный к lease: старый или запоздавший исполнитель с устаревшим token отклоняется |
| **Lease TTL** | Время жизни lease; по истечении агент переходит в read-only (fail-closed). Длинный TTL — медленная остановка, короткий — ложные переходы |
| **Split-brain** | Состояние, при котором два узла считают себя владельцами; предотвращается lease + fencing |

## 5. Безопасность

| Термин | Определение |
|---|---|
| **SPIFFE/SPIRE** | Стандарт и реализация workload identity: каждый агент — своя identity, mTLS между компонентами |
| **Vault** | Хранилище секретов: короткоживущие креды для агентов |
| **JIT-доступ** | Just-In-Time: доступ выдаётся на короткое время под конкретное действие |
| **Prompt injection** | Атака через недоверенные данные (логи, трейсы, комментарии в коде, PR, тикеты), пытающиеся изменить поведение LLM |
| **Структурированный вывод** | Ограничение формата ответа LLM схемой (JSON с валидацией), снижающее риск инъекций |
| **Red-team** | Регулярные атаки на саму платформу: prompt injection, обход политик, атаки через данные |
| **Классы данных** | public / internal / confidential / restricted — определяют, куда может уходить данные (внешний LLM или только локальная модель) |
| **Zero-retention** | Договорённость с провайдером LLM о нехранении отправляемых данных |
| **Data residency** | Требование хранения и обработки данных в определённой юрисдикции |
| **DPIA** | Data Protection Impact Assessment: оценка воздействия на персональные данные (GDPR) |
| **SBOM** | Software Bill of Materials: список зависимостей образа/платформы |
| **Cosign** | Подпись образов контейнеров |
| **SLSA** | Supply-chain Levels for Software Artifacts: провенанс сборки |
| **Trivy** | Сканер уязвимостей образов и зависимостей |
| **Attestation** | Подтверждение целостности агента (например, через TPM/remote attestation) |
| **eBPF** | Технология наблюдаемости ядра: профилирование, трейсинг без агентов в пользовательском пространстве. Ограничения: привилегированный DaemonSet, PII в payload'ах, совместимость с ядрами |
| **WORM-хранилище** | Write Once Read Many: объектное хранилище с object lock для неизменяемого аудита |
| **Hash-chain** | Цепочка хешей записей аудита с подписью ключом из KMS/HSM; корень фиксируется во внешнем WORM |
| **KMS/HSM** | Key Management System / Hardware Security Module: хранение ключей подписи аудита |
| **Decision record** | Запись решения: действие и параметры, инициатор, версия модели, хеш промпта, ID документов контекста, версия политики и вердикт, уровень, lease и fencing token, результат пост-проверки, ссылка на трейс рассуждений |
| **Отравление знаний** | Внесение ложных выводов в базу знаний; защита — утверждение SRE, версионирование, TTL записей |
| **Атака на стоимость** | Зацикливание LLM для исчерпания бюджета; защита — токен-бюджет и лимит итераций |

## 6. LLM-контур

| Термин | Определение |
|---|---|
| **LLM-роутер** | Компонент маршрутизации запросов к моделям по классу данных, сложности, бюджету и LLM-профилю. Роли: local-small, local-large, external-reasoning |
| **LLM-профиль** | Выбор режима (`local-only`, `hybrid` или `off`) и моделей для организации, команды или сервиса. Нижний уровень только сужает верхний; сужение — сразу, расширение — по принципу четырёх глаз с security |
| **Реестр LLM-backend'ов** | Утверждённый список локальных и внешних моделей с юрисдикцией, потолком класса данных и результатами eval. Пользователи выбирают модели только из него |
| **Маскирование PII** | Удаление/замена персональных данных и секретов до отправки во внешний LLM |
| **Local-only режим** | Работа только на локальных моделях (для restricted-данных и изолированных контуров) |
| **Токен-бюджет** | Лимит токенов на инцидент и на период; алерты по стоимости |
| **Eval-контур** | Контур оценки качества ИИ: golden-набор, регрессионный прогон при смене модели/промпта/каталога, red-team, shadow-сравнение |
| **Fine-tuning** | Дообучение модели на валидированной обратной связи (+/-). Не расширяет права и не отменяет политики; eval-гейт перед выкаткой, возможность отката |
| **Shadow-сравнение** | Постоянное сравнение предложений ИИ с решениями SRE |
| **Langfuse / OTel GenAI** | Инструменты трассировки рассуждений LLM (semantic conventions) |

## 7. Тестирование и релизы

| Термин | Определение |
|---|---|
| **Ratchet (трещотка)** | Принцип гейтов: на новом и изменённом коде coverage ≥ 85%, mutation score ≥ 70%; общий показатель проекта не должен падать |
| **Mutation testing** | Проверка качества тестов внесением мутаций в код; инкрементально по diff, полный прогон ночью |
| **Property-based тесты** | Тесты, проверяющие свойства (инварианты) вместо примеров; для критичных путей |
| **Contract testing (Pact)** | Проверка контрактов между сервисами |
| **Canary / Статистический canary** | Постепенная раскатка 5% → 25% → 50% → 100% с анализом на каждой ступени |
| **SPRT** | Sequential Probability Ratio Test: метод раннего останова canary-анализа |
| **Тест Манна–Уитни** | Непараметрический тест сравнения распределений; используется в Kayenta на окнах |
| **Поправка Холма** | Метод коррекции множественных сравнений для canary-метрик |
| **Baseline canary** | Свежий baseline той же старой версии (не весь prod), чтобы прогрев кэшей не искажал результат |
| **Bake-период** | Период наблюдения после 100% раскатки (по умолчанию 60 минут); предыдущая ревизия сохраняется; авто-rollback — L3 |
| **Expand/contract** | Паттерн миграций БД: сначала расширяем схему (совместимо), потом сокращаем старое |
| **Drift detection** | Обнаружение расхождения между GitOps-репозиторием и фактическим состоянием кластера |
| **Shadow-анализ canary («would-have-rolled-back»)** | Прогон анализатора canary на истории релизов без реальных откатов |
| **Fault injection** | Искусственное внесение деградаций для измерения recall rollback'а |
| **Chaos-стенд** | Staging-среда для хаос-тестов (Chaos Mesh, Litmus): утечка памяти, отказ ноды, деградация БД, лавина трафика |
| **Digital Twin** | Цифровой двойник для K8s-уровня; не применяется для Ceph и IPMI (sim-to-real gap) |

## 9. Метрики и качество

| Термин | Определение |
|---|---|
| **MTTR** | Mean Time To Repair: медиана и p90 по классам severity; цель — снижение медианы на 50%+ |
| **Burn rate** | Скорость сжигания error budget по SLO |
| **SLO / SLI** | Service Level Objective / Indicator: целевые показатели доступности и latency |
| **Доля ложных откатов / Recall rollback** | Доля ложных откатов (false positive rate): доля релизов, откаченных без реальной деградации (цель < 5%). Recall: доля пойманных плохих релизов (нижняя граница ≈ 90%). Precision — другая величина: доля действительно плохих релизов среди откаченных |
| **Правило трёх** | При 0 событиях из N односторонняя 95%-граница частоты ≈ 3/N (при 60 действиях ≈ 4,9%) |
| **ДИ Уилсона** | Доверительный интервал для биномиальной пропорции; используется для калибровки порогов G0 |
| **Near-miss** | Блокировка политикой потенциально опасного действия; метрика безопасности |
| **Would-be нарушение** | Нарушение политики, которое произошло бы в shadow-режиме (PEP dry-run): вердикт `deny`. До появления lease (MVP-B) `downgrade` (в том числе из-за `lease_missing`) и `noop` нарушениями не считаются (решение 07.11.2026, утверждено); подсчёт механический: `decision == "deny"`; правило пересматривается при вводе lease в MVP-B |
| **TTL записей** | Срок годности записей в базе знаний; устаревшие требуют ревалидации |

## 10. Режимы деградации

| Термин | Определение |
|---|---|
| **Degraded mode** | Режим при потере связи с Control Plane: вход по истечении lease (не по таймауту пинга); только предодобренные детерминированные действия R1 (R2 если разрешает политика); без свободного reasoning LLM; локальный аудит; reconciliation после восстановления |
| **Reconciliation** | Слияние локальных цепочек аудита с Control Plane и проверка локальных действий на конфликт с текущим состоянием |
| **Песочница (sandbox)** | Изолированная среда для нетиповых действий: staging-реплика, shadow-трафик, стабы внешних зависимостей, маскирование PII, read-only по умолчанию |
| **Предодобренные runbook'и** | Runbook'и с историей успехов, идущие без песочницы (у неё ограниченный бюджет времени в инциденте) |

## 11. Этапы и gates

| Термин | Определение |
|---|---|
| **Этап −1** | Предусловия: согласования security/legal/DPIA, выбор LLM, доступы, целевой поток, метрики, команда, бюджет |

| **Этап 0b** | Shadow Mode: ≥ 4 недель на полном целевом потоке, без исполнения |

| **Gate G4** | Перед fine-tuning: порог объёма данных, преимущество на eval, red-team чист, shadow пройден |
